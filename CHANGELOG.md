# Changelog

All notable changes, including every exported breaking change during v0, are recorded here.

## Unreleased

### Supported behavior

- Experimental Evaluation Model V4 Go client for boolean, choice, and score evaluation questions.
- Public Gateway generation through `POST /v1/responses` and `POST /v1/chat/completions`, with typed buffered and caller-owned SSE streaming calls.
- Staged, experimental `Client.GenerateImage` support for the AI SDK Model V4 provider protocol at `POST /v4/ai/image-model` through `WithBaseURL`. A dynamic `provider/model` ID, 1–16 requested outputs, exact optional request presence, and URL, opaque-base64, or byte image inputs are sent in exactly one request; the client does not fetch URLs, upload files, batch, or retry.
- Staged, experimental `Client.GenerateSpeech` support for the AI SDK Model V4 provider protocol at `POST /v4/ai/speech-model` through `WithBaseURL`. A dynamic `provider/model` ID and exact presence-preserving text, voice, instructions, language, output-format, and finite speed fields are sent in exactly one request; the client performs no automatic batching or retries.
- Staged, experimental buffered `Client.Transcribe` support for the AI SDK Model V4 provider protocol at `POST /v4/ai/transcription-model` through `WithBaseURL`. A dynamic `provider/model` ID and one sealed opaque-string or byte audio input are sent in exactly one request; the client performs no automatic batching, retry, streaming, resume, or replay.
- Staged, experimental `Client.Embed` support for the AI SDK Model V4 provider protocol at `POST /v4/ai/embedding-model` through `WithBaseURL`. A dynamic `provider/model` ID and 1–4096 `Values` are sent in exactly one request for single or many embeddings; the client performs no automatic batching or retries.
- Staged, experimental `Client.Rerank` support for the AI SDK Model V4 provider protocol at `POST /v4/ai/reranking-model` through `WithBaseURL`. A dynamic `provider/model` ID, query, optional `TopN`, and one homogeneous `RerankTexts` or `RerankObjects` envelope are sent in exactly one request; the client performs no automatic batching or retries.
- Separate `WithBaseURL` routing for provider evaluation, image generation, speech synthesis, transcription, embeddings, and reranking and `WithPublicBaseURL` routing for public generation; neither base URL redirects the other contract.
- Typed request, result, metadata, retry-policy, warning, stream, and error surfaces. Responses and Chat function-tool definitions, calls, arguments, and results are transported as data; the SDK does not execute tools.
- Opt-in Chat request-only server-search declarations for `vercel:exa_search`, `vercel:parallel_search`, `vercel:perplexity_search`, and `vercel:tako_search` through `CreateChatCompletionWithServerTools` and `StreamChatCompletionWithServerTools`; hermetic acceptance covers request encoding and validation without claiming hosted live success.
- Additive request-only Responses search support through source-compatible opt-in `ResponsesBuiltInToolsRequest`, `CreateResponseWithBuiltInTools`, and `StreamResponseWithBuiltInTools`: `ResponseWebSearchTool{}` always emits fixed low-context `web_search`; fieldless `ResponseXSearchTool{}` remains unchanged; and `ResponseXSearchOptionsTool` adds the six presence-preserving `x_search` request fields `AllowedXHandles`, `ExcludedXHandles`, `FromDate`, `ToDate`, `EnableImageUnderstanding`, and `EnableVideoUnderstanding`. Nil fields are omitted, present-empty slices emit `[]`, and boolean pointers preserve explicit false/true. Existing methods, results, events, and raw-output boundaries are unchanged. Search executes server-side; the SDK performs no automatic tool execution.
- Credential-free hermetic contract gates cover evaluation, image generation, speech synthesis, transcription, embeddings, reranking, and buffered and streaming Responses and Chat over loopback, alongside separately gated paid live-contract workflows and a clean local-consumer compile gate.
- Successful raw generation JSON, stream events, evaluation, image, speech, transcription, embedding, and reranking bodies, image prompts/URLs/base64/bytes/masks/decoded outputs/usage, speech text/voice/instructions/language/output format/speed/opaque audio, transcription audio/transcript text/segments/language/duration, embedding inputs and vectors, reranking queries/documents/rankings, tool data, headers, identifiers, warnings, and provider metadata remain sensitive evidence boundaries; defensive copies do not sanitize them, and repository gates do not establish hosted-service success.
- Image requests require `Count` in 1–16 and preserve documented pointer and nil-versus-empty presence while omitting present-empty size/aspect ratio and present-zero seed. `ImageURL` is sent without fetching, `ImageBase64` is opaque, and `ImageBytes` is standard-base64 encoded once; the encoded request is limited to 16 MiB. Successful bodies are strictly validated up to 96 MiB and may contain 0–16 outputs independently of `Count`; each output must be strict standard padded base64 and decode to at most 16 MiB, with at most 64 MiB aggregate. Response metadata retains at most 1 MiB. Optional retryability, usage with finite optional numeric token fields, warnings, and provider metadata preserve strict presence rules. `ProviderOption` is sealed with no concrete exported implementation, and `ImageResult` has no output media type.
- Speech requests always emit `Text`, including empty, while `Voice`, `Instructions`, `Language`, and `OutputFormat` omit empty strings but preserve whitespace; non-nil `Speed` preserves any finite value, including zero and negatives. Text and instructions are limited to 1 MiB, voice/language/output format to 255 bytes, and the encoded body to 16 MiB. Successful bodies are strictly validated up to 96 MiB; required `Audio` is an opaque string limited to 64 MiB, is not base64-decoded, and has no media-type field. Response metadata retains at most the first 1 MiB, and warnings/provider metadata use the shared strict presence rules. `ProviderOption` is sealed with no concrete implementation.
- Transcription accepts sealed `TranscriptionBase64` values as opaque valid-UTF-8 data of at most 1 MiB without base64 validation, decoding, normalization, or re-encoding, and `TranscriptionBytes` values of at most 8 MiB that are standard-base64 encoded exactly once. Both variants accept an opaque media type of at most 255 bytes; empty data and media types are allowed, and the encoded body is limited to 16 MiB. Successful bodies are strictly validated up to 16 MiB: text is required, absent segments become a non-nil empty slice, at most 4096 segments contain required text and finite timestamps, and optional language/duration preserve absent or null as nil. Negative, fractional, equal, or reversed timestamps and negative duration are retained. Warnings and provider metadata use strict presence rules, and response metadata retains at most 1 MiB.
- Embedding requests validate each value at 1 MiB and the encoded body at 16 MiB. Successful bodies are strictly validated up to 32 MiB with exactly one finite, nonempty vector per input, while `ResponseMetadata.Body` retains at most the first 1 MiB. Usage absence/null, absent-versus-empty warnings and provider metadata, the closed warning union, and provider metadata object shapes are preserved or rejected rather than repaired. `ProviderOption` is sealed and currently has no concrete implementation.
- Reranking requests accept 1–4096 homogeneous text or JSON-object documents; the query and each document are limited to 1 MiB, `TopN` is optional but bounded by the document count, and the encoded body is limited to 16 MiB. JSON objects are non-null, duplicate-free, strictly bounded, and compacted without changing key order, numeric lexemes, or escape spelling. Successful bodies are strictly validated up to 32 MiB while response metadata retains at most 1 MiB. Rankings retain provider order, require unique exact-integer in-range indices, reconstruct the validated source documents, and accept any finite `float64` score without a 0..1 or descending-order guarantee. Warnings and provider metadata use the shared strict embedding shapes.

### Explicit non-goals

- No public `POST /v1/evaluate` client; its success schema remains blocked on first-party evidence.
- No AI SDK internal `POST /v4/ai/language-model` provider client and no public `POST /v1/embeddings`, image-generation, speech, transcription, or reranking client; public generation uses the distinct `/v1/responses` and `/v1/chat/completions` contracts, while image generation, speech synthesis, buffered transcription, embeddings, and reranking use only their staged provider protocols.
- Responses search support is limited to the documented request fields and the evidenced routes `openai/gpt-5.4-mini` and `spacexai/grok-4.6`. For configurable `x_search`, local option-specific validation rejects only simultaneous non-empty allowed/excluded handle lists; provider-specific limits/defaults, handle syntax and duplicate semantics, date grammar/order/inclusivity/empty meaning, semantic efficacy, wrong-kind server behavior, and fields beyond the documented six remain blocked. `web_search_preview`, omitted/non-low context and other current/preview forms; wider model compatibility, fallback, search-specific selection; and typed search calls/results/actions/posts/sources/citations/annotations/refusals/provider errors/usage/cost or lifecycle events also remain blocked.
- No direct-xAI client or direct-provider compatibility promise. Direct xAI contracts do not establish Gateway option, output, validation, or model support.
- No automatic tool execution, agents, or orchestration; function-tool payload support is data transport only.
- No claim of full Vercel AI SDK or provider feature parity.
- Image, speech, transcription, embedding, and reranking support does not claim JavaScript feature parity, universal model/provider compatibility, concrete provider-specific options, automatic batching, caching, pricing, routing, Gateway fallback, hosted live success, live-service compatibility, release readiness, accepted transcription media types, transcription quality, or output media-type inference. Video generation, streaming transcription, realtime, batches, and management APIs remain absent.
- The full public-generation and provider-evaluation live suites remain **NOT RUN / PENDING LIVE RUN**. No hosted image, speech, transcription, embedding, or reranking success is claimed. The narrow owner-authorized Responses search evidence recorded in `docs/x-search.md` establishes only the documented request declarations on their exact model routes plus sanitized HTTP/status and output-discriminator structure; it does not establish general buffered/streaming Responses or Chat compatibility, Evaluation compatibility, configurable-option semantics or efficacy, wider-model behavior, or typed search outputs/events.

### Experimental status and risk

This is an experimental v0 surface. Exported APIs may change incompatibly during v0, and no v1 compatibility is promised while the evaluation and staged provider-protocol image, speech, transcription, embedding, and reranking contracts remain experimental. The checks and workflows named above describe repository support and release gates; hermetic provider-protocol coverage and the narrow search probes are not evidence of a published release or broader credentialed live-contract success.

### Release status

No public version has been published. Local `origin` is already `git@github.com:EveGoodEvening/vercel-ai-go-sdk.git`; it is not a blocker. Release remains blocked by the owner-selected license, verification of the hosted repository metadata, completed broader authorized live-contract evidence, and reviewed publication/provenance configuration. The narrow search probes do not imply hosted CI, tag, proxy publication, license selection, or release success.

### Migration

Before the initial public release, the module path changed from `github.com/EveGoodEvening/vercel-ai-gateway-go-sdk` to `github.com/EveGoodEvening/vercel-ai-go-sdk`. Consumers of earlier checkouts must update `go.mod` `require`/`replace` directives and Go imports. No exported Go identifiers changed.

The configurable `x_search` request type is additive and source-compatible. Existing fieldless `ResponseXSearchTool{}` calls require no migration, and no method, result, or event contract changed.
