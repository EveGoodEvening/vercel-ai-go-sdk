# Repository Agent Guidance

## Scope

This repository implements a focused Go SDK for three distinct Vercel AI Gateway surfaces: the AI SDK provider-protocol Evaluation Model V4 endpoint, public `/v1/responses`, and public `/v1/chat/completions`, including the documented streaming subsets. Read `planning/IMPLEMENTATION_PLAN.md` before implementation and follow its dependency order, evidence gates, acceptance checks, and commit boundaries. Do not broaden the project into a generic OpenAI client, infer undocumented fields/tools, or claim parity with the JavaScript AI SDK.

## Lessons

- The evidence baseline recorded on 2026-09-20 is `ai@7.0.107`, `@ai-sdk/gateway@4.0.87`, `@ai-sdk/provider@4.0.17`, and `@ai-sdk/provider-utils@5.0.45`. Evaluation entered `ai` in 7.0.103 and Gateway evaluation entered `@ai-sdk/gateway` in 4.0.85. Re-check these versions and upstream source before changing the wire contract.
- The official `@ai-sdk/gateway` provider protocol is not the public OpenAI-compatible `/v1` API. Its default base URL is `https://ai-gateway.vercel.sh/v4/ai`.
- Evaluation Model V4 uses `POST /v4/ai/evaluation-model`. The model ID is carried in `ai-model-id`, not in the JSON body. Required protocol headers include `ai-gateway-protocol-version: 0.0.1`, `ai-evaluation-model-specification-version: 4`, and `ai-gateway-auth-method: api-key|oidc`.
- The evaluation JSON body contains one shared JSON-compatible `state`, a nonempty keyed `questions` map, and optional `providerOptions`. Supported question/answer variants are boolean, choice, and score. The contract includes response validation, optional rounding, usage, warnings, provider metadata, and response metadata.
- `POST https://ai-gateway.vercel.sh/v1/evaluate` is a separate public REST surface whose body includes `model`. It remains unimplemented and evidence-gated because the public success presence/nullability/extension contract is not sufficiently proven. Do not conflate it with provider-protocol `Evaluate` or route it through Chat/Responses.
- Authentication precedence modeled from the official provider is explicit API key, `AI_GATEWAY_API_KEY`, then OIDC when no API key is available. An explicitly selected API key is not silently replaced by OIDC after server rejection. OIDC needs a refresh-capable token source for long-lived clients.
- Model IDs are dynamic `provider/model` strings. A live provider-protocol evaluation on 2026-09-21 confirmed `typesafe-ai/jev`; the previous `typesafe-ai/jev-latest` now returns HTTP 404 `model_not_found`. The SDK must accept arbitrary nonempty IDs instead of freezing a closed enum.
- Native xAI `x_search` is confirmed for direct xAI Responses (`POST https://api.x.ai/v1/responses`) and current `@ai-sdk/xai@5.0.4`. Its raw tool is `type: "x_search"` with fields including `allowed_x_handles`, `excluded_x_handles`, `from_date`, `to_date`, `enable_image_understanding`, and `enable_video_understanding`; output can include provider-executed `x_search_call` items.
- The six configurable fields in direct-provider `@ai-sdk/xai@5.0.4` are candidate vocabulary, not evidence that Vercel AI Gateway `POST /v1/responses` accepts them. Current direct xAI documentation allows up to 20 included/excluded handles and makes the lists mutually exclusive; the pinned SDK caps each list at 10 and does not enforce that exclusion. Do not blend either direct contract into Gateway validation.
- Vercel AI Gateway Responses support is intentionally request-only for fixed low-context `{"type":"web_search","search_context_size":"low"}` and fieldless `{"type":"x_search"}`. The owner-authorized public Gateway probe on 2026-09-21 proved the fieldless `x_search` discriminator for `spacexai/grok-4.6`; it did not prove configurable fields, typed outputs/events, wider compatibility, or direct-xAI support. Preserve fieldless support until exact Gateway evidence clears each field or inseparable option family; then add `ResponseXSearchOptionsTool` rather than changing `ResponseXSearchTool`. Treat evidence field by field: model a single proven value as a fixed type, keep direct-provider provenance separate from Gateway acceptance evidence, preserve unproven outputs raw instead of inferring schemas, and retain no credentials, prompts, generated prose, raw payloads, or sensitive artifact text in repository evidence. Chat request-only declarations for `vercel:exa_search`, `vercel:parallel_search`, `vercel:perplexity_search`, and `vercel:tako_search` remain a separate opt-in surface whose typed outputs, metadata, lifecycle events, and live corroboration are evidence-gated.
- Evaluation is experimental and may change in patch releases. Pin hermetic fixtures to cited upstream versions, keep releases at v0 while the contract is unstable, and require a separately gated live evaluation smoke before release.
- Default retries must remain off because evaluation may be billable and is not known to be idempotent. If callers opt in, retry only classified transient failures with bounded backoff, Retry-After support, and immediate context cancellation.
- Prefer a boring design: one root `gateway` package, small internal HTTP/test helpers, standard library first, private wire DTOs, no JavaScript monorepo mirroring, no automatic tool execution, and no generic cross-surface generation or tool abstraction.
- The repository/module identity is `github.com/EveGoodEvening/vercel-ai-go-sdk`; the root package is `gateway`. The implemented public boundary includes provider-protocol `Client.Evaluate`, public Responses and Chat methods, the request-only Chat server-tool methods for four supported `vercel:*` declarations, and opt-in Responses built-in-tool methods for exact fixed low-context `web_search` and fieldless `x_search` declarations. Public Evaluate, configurable Responses search, other web-search forms, typed search outputs/events, wider model compatibility, and direct-xAI support remain absent and evidence-gated.
- Provider-protocol evaluation and public generation use distinct base URLs and configuration. `WithBaseURL` remains exclusively for `https://ai-gateway.vercel.sh/v4/ai`-style provider endpoints; `WithPublicBaseURL` configures the public `https://ai-gateway.vercel.sh/v1` Responses/Chat origin. Never repurpose one option for the other surface or add `/v4` protocol headers to public requests.
- Responses success decoding is intentionally raw unless a field has exact first-party evidence. Streaming types only the proven `response.output_text.delta` path; other bounded events stay raw. Hermetic handling of raw data or a build-tagged assertion is not proof of live event semantics.
- Chat compatibility uses its own request/result/stream types. Buffered documented fields preserve absent versus null versus value explicitly; streaming types only the proven text-delta subset and `[DONE]` termination. Unknown or undocumented fields remain bounded raw JSON rather than inferred typed support.
- Paid live evidence is a separate release gate. A credential-free fail-closed test, hermetic fixture, compile, or static workflow review never establishes live success. Public-generation and provider-evaluation jobs have distinct acknowledgement sentinels, pinned models, sanitized evidence, and independent review requirements.
- Shared user-facing authentication, endpoint, retry, error, cancellation, and privacy guidance belongs in `docs/client.md`; README and the generation/evaluation guides link there instead of duplicating it. Keep operator checklists and pending hosted evidence in the release/live-evidence docs, not in the quick start. Documentation snippets should compile and use structural-only output; validate them with loopback fixtures rather than paid calls.
- Streaming methods bypass the SDK `RetryPolicy` loop entirely; they do not just disable retries after headers. HTTP execution borrows the configured client's transport, cookie jar, and timeout but overrides redirect handling to return redirects without following them. Ground shared documentation in all implemented surfaces rather than evaluation-only error-operation inventories.
